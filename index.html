Why a Blog?

I fuzz firmware for a living, but writing about it is a different muscle. Explaining a crash well enough for someone else to reproduce it forces me to actually understand it — and firmware security still doesn't have enough plain-language writing out there. I'd rather add to that than not.

Sample: Quick GDB + QEMU Reference for Firmware Debugging

A few commands I reach for constantly when triaging a fuzzer crash on an emulated Cortex-M target:

# Attach GDB to a QEMU gdbserver session
gdb-multiarch ./firmware.elf
(gdb) target remote localhost:1234

# Set a breakpoint at the crash handler and continue
(gdb) break HardFault_Handler
(gdb) continue

# Inspect the fault status register after a crash
(gdb) print/x *(uint32_t*)0xE000ED28

# Walk the stack to find the return address that faulted
(gdb) bt full

# Dump memory around the faulting address
(gdb) x/16xw $sp

Tip: always confirm you're working against an isolated emulation target, never a live device, before you start throwing malformed input at anything.
